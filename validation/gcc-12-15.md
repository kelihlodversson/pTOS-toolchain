# GCC 12–15 bugfix-release validation — 2026-11-11

These recipes add GCC 12.5.0, 13.5.0, 14.4.0 and 15.3.0, rebasing the
CrossMiNT patches for 12.4.0, 13.4.0, 14.3.0 and 15.2.0 respectively.
Official GNU archives and local patches are checksum-pinned. GCC 16.2.0
remains the default; the new releases can be selected in the CLI and manual CI.

The original archived patches are unchanged. The ports retain the full patch
contents, including other language runtime changes, although this SDK builds
C only. GCC 15.3's chrono header needed six remaining `__out` identifiers
renamed after three hunks encountered upstream context changes. GCC 12–14
needed no semantic changes to their existing MiNT patches.

The compiler ports (`dfd9a3a`) and GCC 12 smoke-test adaptation (`b084338`)
were pushed to `gcc-12-15-bugfix` before the pTOS builds and runtime tests.

## Scope and source checks

All four archives passed checksum verification, MiNT patch application and
`prepare.py` target registration for m68k, ARM and x32. The offline
version-selection tests, host checks and patch checksum manifest passed;
the workflow's selectable versions match the recipe catalogue.

The compiler, SDK and runtime results below are for m68k on Linux. Full ARM,
x32 and macOS builds of these four releases were not run. Source preparation
alone does not establish ABI or runtime correctness.

Tested against pTOS `9193f7c7b3773b5cd418144fc8dee6e64c5f1473` in separate
worktrees, with libcmini `c85f67a52679b68782c49fd967732d14bfe87841` and the
existing, unchanged Binutils 2.45 installation. Host GCC was Debian 14.2.0,
QEMU was Debian 10.0.13, and Hatari was 2.6.1-devel at
`23bc3060ebf0da348cc842e358c102ba88002b56`.

Every compiler build included its configured libgcc multilibs. SDK smoke
checks covered ELF, PRG+ELF and GOT/PLT shared-library linking, plus fastcall
attributes and libgcc selection where supported. The volatile-long MMIO and
masked-byte ROM access reproducers passed at both `-O2` and `-Os`; the latter
also passed with each available calling convention. These ports needed no
additional backports of the GCC 16 fixes.

GCC 12's archived MiNT patch does not implement `-mfastcall` or fastcall
multilibs. Its SDK smoke therefore checks the stack ABI. Later tracks must
pass both ABI variants. GCC 12's QEMU configuration is `virt-m68k-cli-elf`;
GCC 13–15 use `virt-m68k-cli-fastcall` with `CONF_WITH_ELF_LOADER=y`, because
this SDK's EmuCON is ELF. The stock fastcall config omits that loader.

Suite counts exclude configuration-specific SKIPs. Every QEMU run also
passed four shutdown probes (poweroff, reboot, cold boot and halt, including
file flushing) and the scalable system-font replay. The runner combines
these under “shutdown checks: 5 passed”.

## Build and runner settings

For each version, the toolchain used separate install and work directories,
reusing Binutils 2.45 from the GCC 16 validation. Builds explicitly selected
the version at both stages and checked `-dumpfullversion` before smoke and
runtime validation:

```sh
./build.sh m68k "$prefix" gcc --gcc "$version"
./build.sh m68k "$prefix" sdk --gcc "$version"
./tests/smoke.sh "$prefix" m68k
```

Builds used `JOBS=2`, cached official archives, locally unpacked MPFR/MPC
headers and bison/flex/m4, and the existing Python environment with kconfiglib.
Each pTOS configuration started with `make distclean`. Common overrides:

```sh
CROSS_COMPILE=m68k-unknown-ptos-prgelf-
CROSSPREFIX=m68k-unknown-ptos-prgelf-
BUILD_TOOLCHAIN_ELF=y
```

QEMU builds additionally used
`LDSO_M68K_PREFIX=m68k-unknown-ptos-prgelf-` and
`TEST_LDFLAGS=-Wl,-q,-Ttext=0,-e,_start`, built `test-dir virt-m68k.elf`, then
ran `tools/run-regression-tests.sh virt-m68k 300`. The `relocprobe2` fixture's
direct ld invocation used `-m m68kmintelf --oformat=elf32-m68k`, as described
in the toolchain README. QEMU's environment preload redirected vvfat scratch
files from read-only `/var/tmp` to `/tmp`. These adaptations stayed in the
validation worktrees and environment.

ROM builds used `TEST_LDFLAGS=-mmintelf -Wl,-e,_start` for their PRG test
programs, built the ROM and `test-hd`, then ran:

```sh
# GCC 13.5 / 14.4 / 15.3: French 192 KB, ST low resolution
python3 tools/run-hatari-tests.py --tos ptos192fr.img --disk test-hd.img --mode low --timeout 600
# GCC 12.5: US 512 KB, STE monochrome/high resolution
python3 tools/run-hatari-tests.py --tos ptos512k.img --disk test-hd.img --mode high --timeout 600
```

The French country choice was set with kconfiglib under `CONFIG_=` (pTOS
uses an empty Kconfig prefix). Both machines used 4 MB RAM. These are emulator
validation results, not hardware tests or performance measurements.
